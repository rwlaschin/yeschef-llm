# Design

## Overview

End-to-end architecture for LLM request handling: UI → Backend → Pub/Sub → Worker → Firestore → UI.

---

## Message Format

**Pub/Sub Message** (published to `{model}_v{version}` topic):

```json
{
  "jobId": "uuid",
  "userId": "user-id",
  "companyId": "company-id",
  "type": "query",
  "userPrompt": "What are the allergen restrictions?",
  "metadata": {
    "optional": "context"
  }
}
```

**Fields:**
- `jobId` — UUID generated by backend, links all related data
- `userId` — User making the request
- `companyId` — Company/organization scope
- `type` — Request type (query, build, recipe, nutrition, substitutes, etc.)
- `userPrompt` — The user's actual question/request
- `metadata` — Optional context (diet codes, preferences, etc.)

**NOT included in message:**
- `model` — Implicit in topic name (which worker receives it)
- `systemPrompt` — Built by backend before publishing

---

## Topic/Model Mapping

Topics are named after the model only. No function type in topic name.

```javascript
// lib/llm/config.ts (in yeschef frontend)
const LLM_CONFIG = {
  openclaw: {
    topic: "openclaw_v1",
    model: "openclaw",
  },
  llama_slim: {
    topic: "llama3_2b_v1",
    model: "llama3.2:2b",
  },
  llama_large: {
    topic: "llama3_3_70b_v1",
    model: "llama3.3:70b-instruct-q4_K_M",
  },
};

export function getTopic(model: string) {
  return LLM_CONFIG[model]?.topic;
}
```

## API Endpoint

**POST /api/llm**

### Request
```json
{
  "userId": "user-id",
  "companyId": "company-id",
  "type": "query",
  "userPrompt": "What are the allergen restrictions?",
  "model": "openclaw",
  "metadata": {}
}
```

### Response
```json
{
  "jobId": "uuid",
  "createdAt": "2026-05-28T...",
  "type": "query",
  "model": "openclaw"
}
```

### Backend Steps

1. **Validate** — userId, companyId, type, userPrompt required
2. **Generate jobId** — UUID (ensures unique, trackable ID)
3. **Look up context** — Query MongoDB + Neo4j for user/company data
4. **Build systemPrompt** — Dynamic prompt based on type + context
5. **Create Firestore doc** — `llmResults/{jobId}` with status: "pending"
6. **Publish message** — To `{model}_v1` topic with jobId, userId, etc.
7. **Return jobId** — To UI for polling/tracking

### Implementation (pseudocode)

```typescript
// app/api/llm/route.ts
export async function POST(req) {
  const { userId, companyId, type, userPrompt, model, metadata } = await req.json();
  
  // 1. Validate
  if (!userId || !companyId || !type || !userPrompt) {
    return Response.json({ error: "Missing required fields" }, { status: 400 });
  }
  
  // 2. Generate jobId
  const jobId = crypto.randomUUID();
  
  // 3. Look up context
  const user = await mongoDb.collection("users").findOne({ _id: userId });
  const company = await mongoDb.collection("companies").findOne({ _id: companyId });
  const perms = await neo4j.runCypher(
    `MATCH (u:User {id: $userId})-[:HAS_ROLE]->(r:Role) RETURN r.name`,
    { userId }
  );
  
  // 4. Build systemPrompt
  const systemPrompt = buildSystemPrompt(type, {
    userName: user.name,
    companyName: company.name,
    userRole: perms[0]?.name,
    ...metadata,
  });
  
  // 5. Create Firestore doc
  await setDoc(doc(db, "llmResults", jobId), {
    jobId,
    userId,
    companyId,
    type,
    model,
    status: "pending",
    createdAt: serverTimestamp(),
    userPrompt,
  });
  
  // 6. Publish message
  const topic = getTopic(model);
  await pubsub.topic(topic).publish(JSON.stringify({
    jobId,
    userId,
    companyId,
    type,
    userPrompt,
    metadata,
  }));
  
  // 7. Return jobId
  return Response.json({
    jobId,
    createdAt: new Date().toISOString(),
    type,
    model,
  });
}
```

## Firestore Schema

### Collection: `llmResults`

**Document ID:** `{jobId}`

**Fields:**
```json
{
  "jobId": "uuid",
  "userId": "user-id",
  "companyId": "company-id",
  "type": "query",
  "model": "openclaw",
  "userPrompt": "What are the allergen restrictions?",
  "status": "pending|streaming|complete|error",
  "response": "The response text, updated in chunks as it streams",
  "error": "Error message if status is error",
  "createdAt": timestamp,
  "updatedAt": timestamp,
  "completedAt": timestamp
}
```

**Status lifecycle:**
- `pending` → message published, waiting for worker
- `streaming` → worker is processing, streaming response
- `complete` → final response received
- `error` → worker failed

## End-to-End Flow

### 1. User submits request (UI)
```javascript
const response = await fetch("/api/llm", {
  method: "POST",
  body: JSON.stringify({
    userId: currentUser.id,
    companyId: currentCompany.id,
    type: "query",
    userPrompt: "Generate 5 lunch recipes",
    model: "openclaw",
  }),
});

const { jobId } = await response.json();

// Store in localStorage for persistence
localStorage.setItem(
  `llm_job_${jobId}`,
  JSON.stringify({ jobId, type, userPrompt, createdAt: Date.now() })
);
```

### 2. Backend publishes message
```
API endpoint publishes to openclaw_v1 topic
Message: { jobId, userId, companyId, type, userPrompt, metadata }
```

### 3. Worker receives message
```
Worker subscribed to openclaw_v1 (via SUBSCRIPTION_NAME=sub_openclaw_v1)
Updates Firestore: status = "streaming"
Streams response chunks to llmResults/{jobId}.response
```

### 4. UI watches Firestore in real-time
```javascript
const unsubscribe = onSnapshot(doc(db, "llmResults", jobId), (doc) => {
  const { status, response } = doc.data();
  
  if (status === "streaming") {
    displayResponse(response);
  }
  
  if (status === "complete") {
    // Clear localStorage
    localStorage.removeItem(`llm_job_${jobId}`);
    unsubscribe();
  }
});
```

### 5. On page reload
```javascript
// Check localStorage for active jobs
const jobs = Object.keys(localStorage)
  .filter(k => k.startsWith("llm_job_"))
  .map(k => JSON.parse(localStorage.getItem(k)));

// Resubscribe to any pending/streaming jobs
for (const job of jobs) {
  onSnapshot(doc(db, "llmResults", job.jobId), (doc) => {
    const { status } = doc.data();
    if (status === "complete" || status === "error") {
      localStorage.removeItem(`llm_job_${job.jobId}`);
    }
  });
}
```

## Spot Instance Resilience

### Message Retry (Pub/Sub)
- Message goes to dead-letter after 5 failed attempts
- Worker crash → message returns to queue automatically
- Worker has 40s ack deadline before retry

### Stale Job Cleanup
- Cloud Scheduler runs every 5 minutes
- Query Firestore: `status == "streaming" AND createdAt < now - 10 minutes`
- Mark as `status: "error"`, `error: "Worker did not complete in time"`

### Idempotency
- Worker uses `jobId` as lookup key
- If message retried, check if `llmResults/{jobId}` already has data
- If so, skip processing (idempotent)

## Execution Model — Dev & Deploy

One build artifact, two run targets. The **Docker image** (Ollama + worker + baked model)
is built once; dev runs it directly, prod bakes it into a VM image for spot instances.

```
build Docker image (Ollama + worker + model baked in — no runtime pull)
   ├─ dev:    waker docker-starts it  ──────────────►  local emulation
   └─ deploy: bake into GCE custom image  ──────────►  spot GPU VMs (MIG)
```

### Wake mechanism (two tiers)

The expensive GPU machine scales **0 ↔ N**; a cheap always-on signal brings it up on
demand. The waker only *triggers* — it never consumes/acks the message; the worker
(once up) is the sole consumer that pulls + acks. This keeps cold-start time off the
Pub/Sub ack lease (the lease clock starts when the worker pulls, post-boot).

| | Wake mechanism | Notes |
|---|---|---|
| **Dev** | a `waker` script polls the emulator subscription; when a message exists and the container is down, it `docker start`s it | faithful stand-in for the prod autoscaler |
| **Prod (Option A)** | **GCE MIG autoscaler** scales spot GPU VMs on the Pub/Sub backlog metric (`num_undelivered_messages`), 0 → N → 0 | raw Compute; spot discount + scale-to-zero, no cluster fee |

### Dev (`scripts/dev.js` + `scripts/waker.js`)

```
start Pub/Sub emulator + create topics/subs   (emulator is ephemeral)
build slim Docker image if missing            (model baked → no pull at start)
start waker → watches sub backlog → docker-starts the container on demand
Firestore = PROD                               (container needs a SA key mounted)
```
- Local Macs have no NVIDIA GPU — dev runs the **slim** model CPU-only (slow but fine).
- Container reaches the host emulator via `host.docker.internal:8085`.

### Deploy (`scripts/deploy.js`, Option A — GCE spot MIG)

```
1. build Docker image  → push to Artifact Registry
2. bake a GCE custom image with the image preloaded on disk (no boot-time pull)
3. instance template: spot, GPU L4(s), the custom image, startup runs the container
4. MIG + autoscaler on Pub/Sub backlog (min 0 → max N)
```

**One VM per replica.** GPU count is the model's "machine description":
- **2B / openclaw** → 1× L4 (`g2-standard-8`)
- **70B** → 2× L4 (`g2-standard-24`, a single box — both GPUs on one VM)

- **Spot preemption is safe:** the worker acks only after the final Firestore write, so a
  preempted job is never acked → Pub/Sub redelivers → another spot VM (same baked image)
  finishes it. `jobId` idempotency guards partial writes. Optionally trap the GCE
  preemption notice to `nack` early for faster redelivery.

> **Note:** distributed/multi-VM "spread" (one model across machines) was considered and
> **rejected** — Ollama doesn't support it natively (it's a llama.cpp-only feature), and
> 70B-Q4 (~40GB) fits a single 2× L4 box (48GB). Keep it simple: one box, both GPUs.

> ⚠️ **Status:** dev (Docker + waker) and the image build/push are implemented. The GCE
> **custom-image bake + MIG + autoscaler** steps are written but **not yet run** — verify
> project params (zone/network/service account/GPU quota) and MIG scale-to-zero (min 0)
> before a real deploy.

## LLM as Tool — Neo4j Meal Plan Constraint Solver

For meal plan generation with complex dietary overlaps, the LLM acts as a reasoning engine that queries Neo4j to find optimal recipe combinations. Rather than pre-filtering recipes in the backend, the LLM uses Neo4j as a tool to solve constraint satisfaction problems dynamically.

> **Scope — this is a separate concern from the Tools Management System.** This is a
> purpose-built, domain-specific feature: hardcoded constraint-solver tools backed by
> Cypher, owned by the meal-planning code. It is **not** authored through the dashboard
> and does **not** share storage, lifecycle, or ownership with dashboard-managed tools.
> The only thing both must respect is the Ollama wire format for a tool *definition*
> (`{ "type": "function", "function": {…} }`) when actually sent to the model — the bare
> `{ name, description, parameters }` and `toolUse` / `tools_enabled` shapes shown here
> are shorthand, not the literal wire format.

### Architecture

**Chef selects:** `["low_sodium", "diabetic", "vegetarian"]`

**LLM workflow:**
1. Receives constraints + access to Neo4j query tool
2. Reasons: "I need ALL recipes matching ALL constraints simultaneously"
3. Calls tool: `queryRecipes(constraints: ["low_sodium", "diabetic", "vegetarian"])`
4. Receives 5,000 matching recipes (not 1M)
5. Reasons: "Which 7-10 recipes maximize ingredient overlap?"
6. Calls tool: `findOptimalCombination(recipes, optimize_for: "ingredient_overlap")`
7. Generates meal plan JSON with daily assignments

### Neo4j Tool Schema

**Available tools the LLM can call:**

### Example Tool Call Flow

```javascript
// LLM receives message:
{
  "jobId": "job-123",
  "type": "meal_plan",
  "userPrompt": "Create a week of meals for low sodium, diabetic, and vegetarian",
  "metadata": {
    "companyId": "org-456",
    "constraints": ["low_sodium", "diabetic", "vegetarian"],
    "planDays": 7
  }
}

// LLM decides to call tool #1:
{
  "toolUse": true,
  "toolName": "queryRecipes",
  "toolInput": {
    "constraints": ["low_sodium", "diabetic", "vegetarian"],
    "maxResults": 1000
  }
}

// Backend executes Cypher:
MATCH (r:Recipe)-[:CONTAINS]->(i:Ingredient)-[:HAS_NUTRITION]->(n:NutritionFact)
WHERE r.low_sodium = true
AND r.diabetic = true
AND r.vegetarian = true
RETURN r.id, r.name, collect(i.name) as ingredients
LIMIT 1000

// Returns ~5K matching recipes to LLM

// LLM then calls tool #2:
{
  "toolName": "findOptimalCombination",
  "toolInput": {
    "recipeIds": ["rec-001", "rec-002", ..., "rec-5000"],
    "planSize": 7
  }
}

// Backend returns best 7 recipes with minimal unique ingredients

// LLM generates final meal plan JSON
```

### Cypher Queries for Tools

**queryRecipes (constraint matching):**
```cypher
MATCH (r:Recipe)-[:CONTAINS]->(i:Ingredient)-[:HAS_NUTRITION]->(n:NutritionFact)
WHERE r.low_sodium = true
AND r.diabetic = true
AND r.vegetarian = true
RETURN r, collect({ingredient: i.name, nutrition: n}) as ingredients
LIMIT $maxResults
```

**findOptimalCombination (minimize unique ingredients):**
```cypher
MATCH (r:Recipe) WHERE r.id IN $recipeIds
WITH r, [(r)-[:CONTAINS]->(i:Ingredient) | i.name] as ingredients
WITH r, ingredients, size(ingredients) as ingCount
ORDER BY ingCount ASC
LIMIT $planSize
RETURN r, ingredients
```

**getNutritionSummary (aggregate nutrition):**
```cypher
MATCH (r:Recipe {id: $recipeId})-[:CONTAINS]->(i:Ingredient)-[:HAS_NUTRITION]->(n:NutritionFact)
WITH r, sum(n.protein * i.quantity) as totalProtein, 
     sum(n.carbs * i.quantity) as totalCarbs,
     sum(n.fat * i.quantity) as totalFat,
     sum(n.sodium * i.quantity) as totalSodium
RETURN {recipe: r.name, protein: totalProtein, carbs: totalCarbs, fat: totalFat, sodium: totalSodium}
```

**checkIngredientAvailability (supplier stock):**
```cypher
MATCH (r:Recipe {id: $recipeId})-[:CONTAINS]->(i:Ingredient)-[:SOURCED_FROM]->(p:ProductSKU)
WHERE p.supplierId IN $supplierIds OR size($supplierIds) = 0
RETURN {ingredient: i.name, available_suppliers: collect(distinct p.supplierName), in_stock_count: sum(p.quantity)}
```

### Error Handling & Fallback

If LLM tool calls fail (malformed Cypher, missing constraints):
1. **Graceful degradation:** Return error message to LLM with suggestion
2. **Retry:** LLM reformulates query and tries again (up to 3 attempts)
3. **Fallback:** If tools unavailable, LLM generates template-based plan from company defaults

### Message Format with Tool Use

**Request with tool capability:**
```json
{
  "jobId": "job-123",
  "userId": "user-1",
  "companyId": "org-456",
  "type": "meal_plan_constraint_solve",
  "userPrompt": "Create a week of low-sodium, diabetic, vegetarian meals that reuse ingredients",
  "metadata": {
    "constraints": ["low_sodium", "diabetic", "vegetarian"],
    "planDays": 7,
    "optimizeFor": "ingredient_overlap"
  },
  "tools_enabled": true
}
```

**Worker publishes tool responses back to Firestore:**
```json

  "status": "streaming",

  "toolCalls": [
    {
      "id": "tool-call-1",
```

# Tools Management System (Dashboard)

> Merged from the former TOOLS_DESIGN.md. Covers the admin UI for authoring tools,
> the stored data model, and the (unbuilt) execution/WASM proposal.

## Overview

A system for defining, managing, and executing tools that Ollama can call. Tools extend Ollama's capabilities by connecting it to external services (databases, APIs, web searches, etc.).

---

## What is a Tool?

A tool has **two parts**:

### 1. **Tool Definition** (Ollama sees this)
```json
{
  "type": "function",
  "function": {
    "name": "web_search",
    "description": "Search the web",
    "parameters": {
      "type": "object",
      "properties": {
        "query": { "type": "string", "description": "Search term" }
      },
      "required": ["query"]
    }
  }
}
```

### 2. **Implementation Details** (Your code needs this)
- Where to call it (HTTP endpoint? Local function? Service name?)
- How to construct the request
- Authentication (API keys, headers)
- Response parsing
- Error handling

---

## Tool Execution Flow

```
User Query
    ↓
Ollama (with streaming enabled)
    ↓
Stream returns: tool_calls + thinking
    ↓
Your code MUST:
  1. Accumulate stream chunks
  2. Extract tool_calls
  3. Execute tool
  4. Append result back to messages
  5. Send back to Ollama
    ↓
Repeat until no more tool_calls
```

> ⚠️ **Reconcile with current worker:** today's worker uses Ollama's **non-streaming** `/api/generate` (see API design above). Tool calling uses the `/api/chat` endpoint with the `tools` array passed **every turn** (tools are stateless — Ollama persists nothing). Streaming (`/api/chat` with `stream: true`) is preferred for UX but **not required** for tool calls. Switching the worker to `/api/chat` is part of the unbuilt executor work.

## Built-in Ollama Capabilities (separate from dashboard tools)

Provided by Ollama itself — **do not rebuild these as custom tools:**

✅ **`web_search` / `web_fetch`** — Ollama's own hosted web search (needs an Ollama API key)
✅ **Vision** — multimodal models read images directly

> Note: this is **distinct from** the dashboard's `web_search` *type* (below), which wraps *your* chosen provider (Google/Bing/etc.) as an ordinary custom tool. Same name, different thing.

## UI (as built)

A **single inline form** (`ToolForm.vue`) — *not* a multi-page wizard:

- **Header** — title (`New Tool` / `Edit Tool v{n}`), Active toggle, close (✕).
- **Row 1** — Tool Name + **Type** dropdown (API Call / Database / Web Search / Transform / Custom). Empty type defaults to **Custom**.
- **Description.**
- **Type-specific implementation fields** — shown for the selected type, each with a docs link.

## Streaming Integration

When tool is called:

```python
# 1. Accumulate stream
for chunk in stream:
    if chunk.tool_calls:
        for tool_call in chunk.tool_calls:
            # 2. Extract tool_call
            tool_name = tool_call.function.name
            arguments = tool_call.function.arguments
            
            # 3. Get tool definition + implementation from DB
            tool = db.tools.findOne({name: tool_name})
            
            # 4. Execute using implementation details
            result = execute_tool(tool.implementation, arguments)
            
            # 5. Append result to messages
            messages.append({
                "role": "tool",
                "content": result
            })

# 6. Send back to Ollama
stream = chat(model, messages, tools, stream=True)
```

## PROPOSAL — Tool Execution & WASM Publishing

> ⚠️ **STATUS: PROPOSAL ONLY. NOT IMPLEMENTED.**
> This section captures a design discussion for how tools will eventually be
> *executed* at runtime (the `custom`/code path). None of it is built. The form,
> CRUD, versioning, and `definition`/`implementation` storage described above are
> the only things that currently exist. This is here so we stop re-litigating the
> architecture — it is a record of decisions, not a spec to implement now.

## Context: the two-part tool (confirmed against Ollama docs)

An Ollama tool is two parts:
1. **Definition** — the JSON schema (`type`/`function`/`name`/`description`/`parameters`) passed to the model. Ollama only ever sees this.
2. **Code** — the function that actually runs when the model returns a `tool_call`. Ollama never runs it; **our worker does**, dispatching by name.

Our `implementation` field is the stand-in for part 2 — typed config now (no-code), with a future `wasm`/code path.

## Ollama runtime facts

- Ollama has **no tool storage/registry/fetching**. Tools are **stateless per request** — the worker passes the `tools` array on every `/api/chat` call.
- Changing the active tool set in our DB → next request carries the new list. That *is* the dynamic loading; nothing is registered into Ollama.
- The only thing not dynamic is the worker's ability to *execute* a brand-new tool — that's the WASM path below.

## Execution strategy (decided directions)

- **HTTP-endpoint-per-tool: REJECTED.** Adds runtime latency and a hard dependency on an external service being up. Breaks cohesion (can't run in dev without that service).
- **WASM: PREFERRED.** Sandboxed, language-agnostic source, hot-loadable, runs in-worker (no network hop). Worker uses Node's built-in WASM runtime.
- **`switch` dispatcher: REJECTED as the end state** — hard-coded, requires worker edits per new kind. Use a **handler registry** so kinds are additive.

## Artifact handling (decided)

- **No code in the database.** Binaries are artifacts; the DB only holds a **reference**, never the bytes.
- **No hard-coded URIs** (e.g. `gs://…`) in the data — that bakes the environment in and breaks dev. Store a **logical key** (`name@version`); an **env-configured resolver** maps it to a backend:
  - dev → local folder (`./tools-artifacts/`), `TOOLS_ARTIFACT_BACKEND=fs`
  - prod → `gs://yc-tools/…`, `TOOLS_ARTIFACT_BACKEND=gcs`
  - (mirrors existing `dotenv-flow` env layering)
- **Integrity via `sha256`** of the module bytes. Same hash guards validation, promotion, deploy preflight, and runtime load. Mismatch = fail closed.

## Two decoupled lifecycles (the key insight)

- **Tool record (the form)** — stable. Name, description, parameters, `type`, **version**. Can exist and be valid with no working code yet.
- **WASM artifact** — churns through builds in dev (throwaway; nothing broken is stored). Only the *working* bytes become an artifact.
- They meet at exactly **one point**: a tool version pins one proven artifact (`name@version` + `sha256`).

## Versioning rule

- **Version bumping happens ONLY in the form** (the tool record owns the version).
- The publish step does **not** invent or bump versions — it publishes against the version the form already set.

## Publishing (proposed mechanism)

One operation, fail-closed:

```
input: working module.wasm + tool name + version (from the form)

1. HASH      sha256(bytes)
2. VALIDATE  instantiate; assert `entry` export; smoke-run vs declared params (time/mem cap)
             ✗ fail → STOP (nothing written) — broken code cannot publish
3. STORE     write bytes to artifact backend as name@version (immutable; no overwrite)
4. BIND      tool.implementation = { type:'wasm', artifact:'name@version', sha256, entry }
```

- **Dev publish:** local CLI → fs backend → dev Mongo. Fast iteration.
- **Prod publish = promotion:** CI only (devs lack prod creds) → re-hash + re-validate the SAME bytes → write to `gs://yc-tools` → prod Mongo. Guarantees dev and prod run byte-identical modules.
- **`sha256` is computed once**, at publish, from the only bytes worth keeping. Never entered by a human; only re-verified downstream.
- **Open question:** prod promotion auto-on-merge vs. manual gated CI approval. (Undecided.)

## Safeguards against shipping half-baked WASM

Four independent, fail-closed gates:
1. **`active` flag** = publish gate (already exists). Drafts stay inactive → never deployed.
2. **Validation gate** — must instantiate + smoke-test before it can go active.
3. **Immutable, hash-locked `name@version`** — a good artifact can't be silently overwritten; changes force a new version.
4. **Devs can't write prod** — only CI has prod-bucket creds; promotion is a reviewed PR.

## Deploy preflight (proposed)

Reconciliation, fail-closed: for every `active` tool, verify its artifact exists in the target backend AND its `sha256` matches AND it instantiates. Any miss → **abort the deploy** (never start).

## Proposed `implementation` shape (WASM, future)

```json
"implementation": {
  "type": "wasm",
  "artifact": "search_recipes@1",
  "sha256": "abc123…",
  "entry": "run"
}
```

No model/form change needed to adopt this later — it's additive (`type: 'wasm'` + a resolver + the registry).
