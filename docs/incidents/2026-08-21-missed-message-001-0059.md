# Production evidence: run `001-0059` was leased behind a runaway generation

Captured: 2026-08-21 UTC  
Project: `yeschef-c572a`  
Incident window used for metrics: `2026-08-21T07:30:00Z`–`08:00:00Z`

This receipt is deliberately separate from the runaway-generation diagnosis for runs
`001-0004` and `001-0079`. It records the transport history of `001-0059` only. No machines were
started, no messages were pulled, and no jobs were rerun while collecting this evidence.

## Classification

`001-0059` was **published, delivered, and leased by a worker, but never started at the model gate
and never acknowledged**. It was not dead-lettered. The receiving worker already had its only
generation slot occupied by a runaway generation, yet the process had leased a second message.
The Pub/Sub client kept that queued message's lease extended until the worker was terminated. With
the production workers then stopped, no live consumer took the redelivery before the Firestore slot
was manually marked failed.

This is therefore not “never published,” “published but not delivered,” or “acknowledged without a
terminal result.” It is the **leased/stranded** case. “Lost” applies at the application-observation
layer—the slot remained `running` with no response—not as proof that Pub/Sub discarded the message.

## Delivery-attempt limit

The exact Pub/Sub `deliveryAttempt` number for `001-0059` cannot be recovered from the retained
evidence. The worker logged `message.deliveryAttempt` only for malformed JSON, not for normal
deliveries, and Pub/Sub does not expose the counter after the fact through subscription metadata or
aggregate monitoring. The one normal delivery is directly observed at `07:37:41.755Z`; no
redelivery is present in logs before all workers were stopped. Do not substitute semantic
`payload.attempt: 0` for Pub/Sub's delivery-attempt counter—they are different fields.

## Root cause and corrective direction

The deployed worker admitted two handlers (`inFlight=2`) while its model generation gate was one
slot (`1/1 busy`). Pub/Sub flow control therefore leased work that the process could not begin and
auto-extended that lease while it waited behind a runaway generation. When the process was
terminated, the queued message had no opportunity to complete, ack, or report a terminal Firestore
result.

The corrective invariant is: **a worker must not lease more model messages than it can actively
generate**. Pub/Sub `flowControl.maxMessages`, the in-process generation gate, the model's
`OLLAMA_NUM_PARALLEL`, and autoscaler messages-per-instance must derive from one value. Shutdown
must also release or nack queued-not-started messages before exit, or stop pulling before shutdown
and wait only for work that has actually entered generation.

The current workspace already contains lease-bound code and commentary expressing this invariant.
Those pre-existing changes were not authored or deployed by this evidence-gathering task, and this
receipt does not claim production is fixed. Production verification requires a separately approved
deployment and a controlled queue test; no such action was performed here.
